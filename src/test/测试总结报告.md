# 后端自动化测试总结报告

**范围**：`src/backend/tests/` 下的 **单元测试**（`unit_test/`）与 **集成测试**（`integration_test/`），基于 `pytest`。  
**需求依据**：系统功能需求（FR-01～FR-13）与非功能需求（NF-01～NF-13）；详细用例与测试文件对照见 `backend/tests/FR_NFR_TEST_MAPPING.md` 及附录 LaTeX（`appendix_unit_tests_latex.tex`、`appendix_integration_tests_latex.tex`）。

---

## 1. 单元测试（Unit Test）测了什么

单元测试在 **不连接真实 PostgreSQL、ComfyUI、和风天气 API** 的前提下，对 **可独立验证的后端逻辑** 做输入输出或异常断言；数据库与外部依赖通过 Mock / Patch 隔离。

| 方面 | 说明 | 与需求的对应关系（摘要） |
|------|------|--------------------------|
| **认证与安全** | JWT 创建与校验、密码哈希、`authenticate_user`、`get_current_user` 等依赖注入路径 | **FR-01**（登录会话基础） |
| **数据校验与 Schema** | 用户注册/登录、天气查询参数、`ChatReq` 等 Pydantic 模型 | **FR-01、FR-05、FR-06** 等 |
| **衣橱业务逻辑** | 衣物分类归一化、季节表单解析、CRUD 错误路径与边界 | **FR-02、FR-03、FR-13**（逻辑层；非完整上传链路） |
| **推荐与 AI 消息** | 回复语言判定、Agent 上下文构建、数据库检索辅助、LLM 返回 JSON 归一化（`build_ai_message`） | **FR-05、FR-07、FR-08、NF-07**（后端语言策略） |
| **天气相关逻辑** | 与 agent 侧一致的天气数据“当日新鲜度”等规则（测试内镜像实现） | **FR-06** |
| **虚拟试衣准备** | ComfyUI 工作流模板映射、`clean_token` 等 | **FR-10、FR-11**（管线准备，非真实出图） |
| **横切能力** | 统一异常、响应封装、密码重置 Token Schema、风力等级文案等 | 支撑多模块稳定性 |

**单元测试刻意不覆盖**：真实 LLM 推理、真实向量库/Chroma 全链路、完整 multipart 上传落库、性能与并发指标（见下节 NFR）。

## 2. 集成测试（Integration Test）测了什么

集成测试使用 **FastAPI `TestClient`**，挂载 **单一路由子应用**（`integration_test/minimal_apps.py`），**不** `import app.main`，避免测试时执行全量 `create_all`。数据库与重依赖仍以 Mock / Patch 隔离；**集成的是 HTTP 层 + 路由 + 依赖注入与处理函数**，不是端到端真机全栈。

| 方面 | 说明 | 与需求的对应关系（摘要） |
|------|------|--------------------------|
| **认证与用户** | 注册、登录、Token 校验、忘记密码（身份匹配重置）、`GET/PATCH /api/users/me` | **FR-01、FR-04** |
| **推荐 AI** | 对话列表/创建/删除、`POST /api/ai/chat/stream` 的 SSE 形态（Agent 侧 Mock） | **FR-05、FR-08** |
| **衣橱与日历/分析** | `GET /api/clothing`（列表与筛选参数下传 CRUD）、日历穿搭列表、分析摘要接口契约 | **FR-13** 及衣橱洞察相关 |
| **天气** | `GET /api/weather/now` 委托服务层（服务 Mock） | **FR-06** |
| **虚拟试衣与模特照** | 试衣 generate/upload-image 路由、模特照上传 API | **FR-10、FR-11**（路由契约；生成服务 Mock） |
| **范围说明** | 用例与 **当前前端已调用的接口** 对齐；未在前端调用的批量删除/更新等未列入本集成套件 | 保证“接口—前端”一致性 |

## 3. 与需求（Requirements）的对应方式

### 3.1 功能需求（FR）

- **有直接自动化覆盖的 FR**：通过上表中的单元测试 **和/或** 集成测试共同覆盖（例如 FR-01 单元测 JWT/认证逻辑，集成测 HTTP 注册登录）。  
- **仅有单元、无集成**：如部分 **FR-02**（表单字段与 CRUD 错误）、**FR-03**（解析类逻辑，不含视觉模型）。  
- **仅有集成或偏契约**：如 **FR-04**（用户资料 HTTP）、部分 **FR-13**（列表 GET；批量接口因前端未接而不测）。  
- **当前无专用自动化**：**FR-07**（推荐条数依赖 LLM）、**FR-09**（无专用反馈学习 API）、**FR-12**（后端无分享链接 API）等——需在文档中标注为 **手动 / E2E / 未来补充**。

### 3.2 非功能需求（NFR）

| 类型 | 与当前 pytest 的关系 |
|------|----------------------|
| **性能（NF-01～NF-03）** | **未** 用本仓库 pytest 覆盖；需压测、计时或专用工具。 |
| **可用性/运维（NF-10）** | 当前套件 **未** 包含健康检查集成用例（与前端未调用 health 一致）；线上 SLA 依赖监控。 |
| **体验与多端（NF-04～NF-06、NF-12、NF-13）** | 以前端/E2E/手测为主。 |
| **安全与合规（NF-08、NF-09）** | 以政策与代码审查为主，pytest 无法单独证明。 |
| **语言（NF-07）** | 后端 **单元测试** 覆盖回复语言判定逻辑；界面中英文切换需前端验证。 |

## 4. 执行与环境说明

- **命令**（在 `src/backend` 目录）：`python -m pytest tests -q`  
- **依赖**：见 `backend/requirements.txt`；使用 Starlette `TestClient` 时 **httpx 版本需低于 0.28**（已在 requirements 中约束为 `httpx>=0.27,<0.28`），否则会出现 `Client.__init__() got an unexpected keyword argument 'app'`。  
- **详细映射表**：`backend/tests/FR_NFR_TEST_MAPPING.md`。

---

## 5. 结论（简要）

- **单元测试** 保证核心业务逻辑、校验与推荐相关纯函数在隔离环境下行为正确，对应需求文档中可分解为“函数级”的 FR 及 **NF-07** 的后端部分。  
- **集成测试** 保证 **前端实际使用的一组 REST/SSE 接口** 在 Mock 环境下的契约与主流程正确，对应 **FR-01、FR-04～FR-06、FR-08、FR-10～FR-11、FR-13** 等与 HTTP 相关的条目。  
- **大量 NFR** 与 **部分 FR** 仍依赖手动测试、E2E、压测或运维数据，不在当前 pytest 范围内；与《测试计划》中的范围与交付物一致，可作为《测试总结报告》中“自动化覆盖”与“待补项”的分界线。
